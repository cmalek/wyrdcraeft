# Canonical morphology DB uses startup Alembic migrations

`wyrdcraeft` will treat app-data `wyrdcraeft.sqlite3` as one canonical working database for morphology, attached dictionary, and derived lexicon data, and every DB-using command will ensure it is at Alembic head before use. We chose this over per-command path overrides and ad hoc schema setup because lexicon browse depends on all three data sets together, schema changes must not force hand-rebuild surprises, and one startup migration path lets us take one pre-migration backup, restore on failure, stop, and print one rebuild recipe when a legacy pre-Alembic database must be reset. Older `morphology.sqlite3` files from before the rename will be treated as legacy input instead of renamed in place: back them up, create fresh canonical schema in `wyrdcraeft.sqlite3`, stop, and require rebuild. Successful migrations keep one backup and ask on the next interactive invocation: `Found backup database from ${date}, caused by migration to ${version}. Delete it? Answer \`y\` if you have used wyrdcraeft successfully since the last migration. [y/N]`. Startup migration flow must also narrate its decision path and progress clearly so users can see why migration is needed and what stage is running. We will also standardize long-running DB-producing commands on the subcommand name `build` so the rebuild recipe stays memorable: `morphology build`, `dictionary build`, `lexicon build`. Those build commands remain separate on purpose so rebuilds stay explicit and debuggable.
